# Dev Log

Running log of what happened in each Claude Code session in this repo. Short entries only — a few bullets, not a report. Newest entries at the bottom (append-only, so concurrent sessions never clobber each other).

## How to log an entry (read this before writing)

1. Append only. Never rewrite this file wholesale (no full-file `Write`) — that can silently drop another session's entry that landed while you were working. Always add your entry with a shell append (`cat >> DEVLOG.md <<'EOF' ... EOF`), never the Edit/Write tools on this file.
2. Take the lock first, so two sessions logging at the same moment don't interleave mid-entry:

```bash
cd /Users/judes/Downloads/Bubu-Motion-v1-main/Bubu_Motion
# acquire lock (mkdir is atomic); break stale locks older than 2 min (crashed session)
while ! mkdir .devlog.lock 2>/dev/null; do
  if [ -n "$(find .devlog.lock -maxdepth 0 -mmin +2 2>/dev/null)" ]; then
    rmdir .devlog.lock 2>/dev/null
  fi
  sleep 1
done
trap 'rmdir .devlog.lock 2>/dev/null' EXIT

cat >> DEVLOG.md <<'EOF'

## YYYY-MM-DD — short title
- what changed / decided
- why (if not obvious)
- next step, if any
EOF

rmdir .devlog.lock
```

3. Entry format: `## YYYY-MM-DD — short title` header, then 2-5 bullets. Skip sections that don't apply. No fluff, no restating the diff — just what a future session needs to know.
4. At the **start** of a session, read this whole file for context before doing other work.
5. Log at the **end** of a session, or right after finishing a meaningful chunk of work — not after every trivial edit.

## 2026-09-02 — Diagnosed "Sending failed" session drops; fixed trigger + fail-fast
- Root cause of `Lỗi: Sending failed, please check the network` is **not** the network. `esp-aes: Failed to allocate memory` → `esp-tls write error -0x0001` → WS send fails. The S3 AES accelerator can only DMA from internal SRAM, but `CONFIG_MBEDTLS_EXTERNAL_MEM_ALLOC=y` (sdkconfig.defaults.esp32s3) puts mbedtls buffers in PSRAM, so every TLS record needs a small internal `MALLOC_CAP_DMA` allocation. Internal heap was at ~8-35KB (largest block 8192) when AFE + multinet had just allocated, and the allocation failed.
- Trigger is always the same payload: the MCP `tools/list` reply — 19 tools, 5485 bytes of tool JSON, one frame, sent immediately on every connect. Both failures in the user's log were this exact message.
- Fix 1: `McpServer::GetToolsList` `max_payload_size` 8000 → 1800 (mcp_server.cc:1089). The `nextCursor` pagination was already implemented and correct; it just never kicked in. Now 4 pages of ~1920 bytes each (incl. jsonrpc + session envelope), all well inside one 4096-byte TLS record. Verified largest single tool is 638 bytes vs a ~1760 effective ceiling, so no tool can ever trip the "payload size limit" error path.
- Fix 2: `WebsocketProtocol::SendText` retried 3x with a 50ms gap instead of `SetError()` on the first failure. **Guarded to frames ≤ CONFIG_MBEDTLS_SSL_OUT_CONTENT_LEN − 8**: above that mbedtls splits the payload across records and `EspSsl::Send` (managed_components/78__esp-ml307) discards how many bytes of a split write already hit the socket, so a blind resend would duplicate them and corrupt the WS stream. Checked mbedtls `ssl_write_record`: on encrypt failure it returns before `out_left +=` and before the seq-number bump, so the single-record retry is byte-safe and leaves no counter skew.
- NOT done (user deferred): `CONFIG_MBEDTLS_HARDWARE_AES=n` (software AES needs no DMA-capable memory — the actual cure, the above only lowers the odds) and `CONFIG_SPIRAM_TRY_ALLOCATE_WIFI_LWIP=y` (frees internal SRAM). Same memory squeeze is the likely cause of the OTA stall: internal low-water hit 8375 bytes mid-download and the 3.6MB GitHub fetch died after 16384 bytes on the 30s HttpClient read timeout.
- Two side notes for future sessions: (1) `gdma_link_mount_buffers: no more space` is the LCD i80 driver, not AES — IDF creates its link list with `check_owner=true`, so a mount fails if the prior frame's DMA hasn't returned descriptor ownership. Cosmetic, one dropped frame. (2) `esp32s3_round_i80_board.cc:724` sets `.psram_trans_align = 64`, which in IDF 5.5 is a **deprecated union member sharing storage with `dma_burst_size`** — it's actually setting a 64-byte DMA burst, and `.sram_trans_align = 4` is silently ignored.
- Built clean, no warnings. NOT flashed or tested on hardware yet.

## 2026-09-02 — Uplink livelock: one failed SendAudio wedged listening forever
- Symptom on hardware after the tools/list + SendText fixes: device reached `listening`, ran ~8.5 min, then spun forever on `AudioService: Encode queue full, dropping oldest uplink frame` at the 60ms frame rate. Not a regression — a pre-existing livelock the earlier fix merely let us reach, because sessions now survive past connect instead of dying in the first second.
- Chain: `MAIN_EVENT_SEND_AUDIO` is set from exactly one place (`on_send_queue_available`, application.cc:129), which is called from exactly one place (`OpusCodecTask` after a successful push, audio_service.cc:556), which can only push while `audio_send_queue_.size() < MAX_SEND_PACKETS_IN_QUEUE` (2400/60 = 40). The drain loop `break`s on the first `SendAudio` failure, leaving 40 packets queued → codec task blocks on its cv → callback never fires again → main task never drains again. Encode queue (cap 2) then overflows every frame, forever. Main loop stays alive the whole time (1Hz clock tick), so it looks like a hang rather than a crash.
- Fix: the drain loop now always empties the send queue, counting drops instead of bailing out (application.cc). Uplink is realtime so frames behind a failure are stale anyway; the point is that the queue must never be left full. Self-heals on the next event since `send_failed` is per-iteration.
- Deliberately did NOT add a retry to `SendAudio` the way `SendText` got one: for realtime media, dropping a frame beats stalling the main task 100ms and delaying every frame behind it. Log line is now `[AI-TX-AUDIO] sent=N dropped=N failed=bool`.
- The underlying `SendAudio` failure is almost certainly the same AES/internal-SRAM squeeze as before (audio frames are ~60-120 bytes, always one TLS record, no retry, no error surfaced). This is now the strongest argument for `CONFIG_MBEDTLS_HARDWARE_AES=n` — still not applied.
- Built clean. NOT yet flashed/tested.

- **TRAP worth remembering: enabling `SPIRAM_TRY_ALLOCATE_WIFI_LWIP` flips WiFi TX buffers from dynamic to STATIC, and turning the option back off does NOT restore them.** Kconfig left `CONFIG_ESP_WIFI_STATIC_TX_BUFFER=y` / `..._NUM=16` behind = 16 × 1600B = ~25KB of internal DMA RAM gone permanently. Looked exactly like NVS corruption; wasn't. Found by diffing good vs bad boot logs — the tell was one line: `wifi:Init static tx buffer num: 16`.

Restored from `sdkconfig.before-aes-fix.bak`; verified back to `Init dynamic tx buffer num: 32`, free internal 48443 / low-water 22359 at idle, ~20KB steady / 2931 low-water, OTA config fetch OK, no MQTT fallback.

Next step is data, not config flags: `heap_caps_print_heap_info(MALLOC_CAP_INTERNAL)` plus task stack high-water marks at the moment of failure, to find who transiently eats ~17KB.

## 2026-09-02 — Heap instrumentation added; found ~50KB of internal RAM in unused task stacks

Wired into `app_main`, the first failed `SendText` attempt, and auto-fired by the sampler on any failure anywhere. `SystemInfo::PrintHeapStats` now also logs largest-free-block and the DMA pool — that is the number that predicts the AES failure, not total free.
- **Sampler stack MUST live in PSRAM** (`xTaskCreateWithCaps(..., MALLOC_CAP_SPIRAM)`). With a normal 4KB internal stack the probe shifted free internal from ~21KB to ~13KB — it was distorting the very number being measured.
- **Gotcha: `CONFIG_NEWLIB_NANO_FORMAT=y` means no `%lld` in printf/ESP_LOG.** All int64 timestamps printed as literal "ldms". Cast to `(unsigned)` and use `%u`.
- **Main finding — over-provisioned task stacks.** At failure: `sfx_codec` unused=23360, `opus_codec` unused=16692, `ai_chat_runtime` unused=10636 — ~50KB of internal SRAM sitting in stack that is never touched (FreeRTOS stacks are internal by default). Meanwhile `ipc0` unused=412, `ipc1` unused=548, `IDLE0` 724, `IDLE1` 732 are uncomfortably thin. Trimming the three fat ones, or moving them to PSRAM via `xTaskCreateWithCaps`, is the obvious next fix.
- Heap is also badly fragmented: region 0x3fcf0000 (32KB) has 788 alloc_blocks / largest free 368B; 0x3fce9710 (22KB) and 0x3fcb07b8 (233KB) are ~100% allocated. DMA totals `min_free 635` bytes since boot.
- Caveat on the hook: the one failure caught was `size=352 caps=0x804` (INTERNAL|8BIT, **no DMA bit**) — so NOT the AES allocation. Most likely IDF's small-allocation internal-first attempt falling back to PSRAM (benign, `SPIRAM_MALLOC_ALWAYSINTERNAL=2048`), but it still shows how starved internal RAM is. Expect benign hits; check the caps before concluding.
- That capture had **no `esp-aes` failure and no "Encode queue full"** — session opened, held listening 23s->59s, closed clean. So the restored config + fixes 1&4 work; the AES failure is intermittent and still needs to be caught in the act.

## 2026-09-02 — Trimmed task stacks: internal SRAM 21KB -> 50KB, low-water 2.1KB -> 36KB
- Root cause of the internal-SRAM shortage was never a leak or a transient spike: **three task stacks were statically over-provisioned by ~50KB**, and FreeRTOS stacks are internal RAM. Measured high-water (bytes, see note below): `sfx_codec` used 1216 of 24576, `opus_codec` 7884 of 24576, `ai_chat_runtime` 1652 of 12288.

## 2026-09-03 — Dead mic in listening: root-caused, plus a correction to the stack-trim entry
- **Symptom:** session reaches `listening` (mode=1, ManualStop), mic delivers ~50ms then nothing for 35s+, `processor=false`, `enc_q=0 send_q=0`, never recovers. Chain: `AfeAudioProcessor::Initialize()` bails (almost certainly `create_from_config` → nullptr under internal-RAM pressure) → `GetFeedSize()` returns 0 → `EnableVoiceProcessing(true)` returns early clearing `AS_EVENT_AUDIO_PROCESSOR_RUNNING` → `AudioInputTask` parks forever on `xEventGroupWaitBits(TESTING|WAKE_WORD|PROCESSOR, portMAX_DELAY)` → nobody calls `ReadAudioData`, so `last_input_ms_` never updates. The mic is not broken; nothing is pumping it.
- **How to spot it in a log without the ERROR line:** `AfeAudioProcessor::Initialize` ends by creating the **`audio_communication`** task, and `AudioProcessorTask()` is a `while(true)` that never exits — so once created it is permanent. HeapDebug enumerates via `uxTaskGetSystemState` (complete list). No `audio_communication` row ⇒ Initialize bailed. (`audio_detection` missing is a red herring: `CONFIG_USE_CUSTOM_WAKE_WORD=y`, the AFE wake word isn't built.)

Replaced with `AudioService::EnsureAudioProcessorInitialized()`, which gates the flag on `GetFeedSize() > 0` and retries on every call until it takes.
- **Fix 2 — CORRECTION to the 2026-09-02 stack-trim entry: that trim did NOT stick.** A later session reverted it and left a `DO NOT trim` comment at audio_service.cc — `opus_codec` at `2048*6` **overflowed as soon as the encode path first ran** (connecting → listening, AFE start); the 7884-byte sample behind the trim had only ever seen decode. Real peak >12288. Do not re-apply it. ## 2026-09-03 — SFX glitching: the overlay lane assumed 60ms packets, assets are 20ms
- **Root cause of the crackle heard partway through most SFX:** every asset in `main/assets/common` is encoded as **20ms** Opus packets (verified by parsing their TOC bytes; all are 16kHz mono, matching `AUDIO_OUTPUT_SAMPLE_RATE`, so resampling is not involved). `PlayOverlaySound`'s demuxer callback hardcoded `packet->frame_duration = 60`, and every queue bound counted in "packets" inherited that error.
- The damage is in `MAX_SFX_PLAYBACK_TASKS_IN_QUEUE = 2`: intended as 120ms of decoded PCM, actually **40ms**. That buffer is filled by `SfxCodecTask`, the lowest-priority audio task (prio 3, vs opus_codec 5 / audio_output 4 / audio_input 8), contending with taskLVGL and the AFE `audio_communication` task. Any scheduling gap over 40ms underruns I2S → audible glitch. Raised to **12 (~240ms)**, ~9KB while a clip plays, nothing at idle.
- Added `OpusPacketDurationMs()` (RFC 6716 §3.1 TOC parse: config → frame size, code → frame count) and used it in the overlay demuxer callback so `frame_duration` is read off the packet instead of assumed. Falls back to `OPUS_FRAME_DURATION_MS` if unparseable.
- **Deliberately did NOT grow `MAX_SFX_DECODE_PACKETS_IN_QUEUE`.** Left at 333. The old `20000/60` expression claimed 20s of backlog but at 20ms packets buys 6.6s, so `bubu_sing3` (15.3s) and `bubu_sing4` (17.1s) already truncate. Fixing that by growing the queue would park ~100KB in INTERNAL RAM (payloads ~79B, under `CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL=2048`) — the exact pool AFE needs. Real fix is incremental demuxing rather than parsing a whole clip synchronously into the queue.
- **Left the voice lane alone on purpose.** `PlaySound` has the identical hardcoded 60 and a 2-deep playback queue, so local main-lane sounds (popup/success/exclamation) have the same latent shallowness — but that queue is shared with network TTS, where changing frame_duration forces a mid-stream decoder reopen. Not worth the blast radius in the same change.
- Built clean. NOT flashed. If glitching survives this, revert the PSRAM `sfx_codec` stack from the previous entry first — it is the other unverified variable in this lane.

## 2026-09-08 — Root-caused and fixed "KHÔNG CÓ WIFI" / permanent connectivity loss: WiFi scan never restores the station

## 2026-09-08 — Memory census: internal SRAM is full BY POLICY (ALWAYSINTERNAL=2048) while PSRAM sits 60% free
- Full inventory of the board's memories. **Internal SRAM is the only one in trouble**: 280 KiB of heap at boot (227+21+32 KiB regions), down to 38.7 KB free at activation, 22.3 KB after multinet, and **5.5-9.1 KB in idle steady state with the largest contiguous block at 1920-2304 B** (`minimal sram` has touched **23 B**). Everything else is roomy: PSRAM heap 4696 KiB with ~1.87 MB free (59% used), app partition 3583 K of 5632 K (64%), RTC FAST/SLOW ~0.5%. Second-fullest is the **assets partition at 87.9%** (assets.bin 4386 K in a 4992 K spiffs) — not urgent but only ~600 K of headroom left. Flash is 100% allocated across partitions, no spare region.
- **The finding that reframes the whole RAM problem: `CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL=2048`.** Every allocation smaller than 2048 B is *forced* into internal RAM; only bigger ones are allowed to land in PSRAM. So internal RAM drowns in small objects (map nodes, std::string, task TCBs, small buffers) while 1.87 MB of PSRAM goes unused. It also produces a nasty regime: once the largest free internal block falls to 1920 B — *below* the 2048 threshold — small allocations start failing while large ones still succeed in PSRAM. Cheap levers, in order: lower `ALWAYSINTERNAL` (2048 -> 512/256), set `CONFIG_SPIRAM_TRY_ALLOCATE_WIFI_LWIP=y` (still off; WiFi/LWIP buffers are pinned internal today), drop `CONFIG_MBEDTLS_SSL_IN_CONTENT_LEN` from 16384. Each needs an on-device audio check since PSRAM is slower.
- Measured internal-RAM consumers: boot->activation eats 241 KB of the 280 KB (drivers/LVGL/WiFi/tasks); **multinet costs 16,076 B internal + 2.36 MB PSRAM**; `AudioService` task startup (8.8s -> 17.9s) costs a further **13,236 B**.
- **Wake-word grammar trimmed 8 phrases -> 4** per user request. ## 2026-09-08 — Static memory audit from the map file: the app image is mirrored into PSRAM, and a 160KB iostream accident
- **The structural fact the earlier census missed: `SPIRAM_FETCH_INSTRUCTIONS=y` + `SPIRAM_RODATA=y` copy the whole app `.text`+`.rodata` into PSRAM at boot** — `.ext_ram.dummy = 3,604,448 B (3520 KiB)`, which is exactly the 8192-4696 KiB gap in the measured PSRAM heap. **So every KB of code/rodata costs 1 KB of flash AND 1 KB of PSRAM.** That reframes every code-size question as a PSRAM question.
- **Best lever found, low risk: two `std::stringstream` uses (`ota.cc:523`, `afe_wake_word.cc:60`, both just splitting a string) drag in libstdc++'s locale/iostream cluster** — `locale-inst` + `wlocale-inst` + `cxx11-*-inst` + `shim_facets` + `sstream-inst` ≈ **160 KB flash + 160 KB PSRAM + ~4.3 KB internal SRAM** (`locale_init.o` alone is 3,544 B of `.bss`). Replace both with `strtok_r` and the whole cluster unlinks.

- **Flash is 100% allocated with a bad split**: `ota_0`/`ota_1` are 5632 K each holding a 3583 K image (63.6%, so 2 MB idle per slot) while `assets` is at **87.9%** (4386 K of 4992 K). Rebalancing needs a partition-table change, which **OTA cannot deliver**, so it must be decided before mass production.
- `assets.bin` breakdown (36 files): `srmodels.bin` 2126 K, `font_puhui_common_20_4.bin` **1211 K** (a CJK font on a Vietnamese product; `font_puhui_basic_20_4` is another 119 K inside the app as the theme's `BUILTIN_TEXT_FONT`), 12 menu/sub_care PNGs at 240x240 truecolor **990 K total** (67-108 K each, palette-quantizing typically cuts 60-70%), 25 emoji PNGs 59 K.

## 2026-09-09 — Assets downloads now verified with SHA-256; corrupt-bundle and auto-retry paths proven on hardware
- **A correction to my own framing first.** I told the user a corrupt download could latch `applied_url` and brick the assets partition permanently. Reading further: `Assets::Download()` ends by calling `InitializePartition()`, which **does** return false on a checksum mismatch, so `applied_url` is only written for a bundle that passed. The real gap was never the ordering — it was that the only integrity check is `LvglStrategy::CalculateChecksum`, a **16-bit additive sum** (`checksum & 0xFFFF`): a 1-in-65536 miss rate and structurally blind to byte reordering.
- **Fix: the server now supplies a SHA-256 and the device verifies it while streaming.** `Assets::Download()` gained an `expected_sha256` parameter and hashes each block with mbedtls (`MBEDTLS_HARDWARE_SHA=y`, so it is nearly free next to the flash erase it sits between). Checked **before** `InitializePartition()`, so a bad bundle reports as a hash mismatch rather than the vaguer downstream checksum failure. An empty hash means "none offered" and logs a warning naming the digest it computed.
- Plumbing: gateway `assets: {url, sha256}` (from the generator manifest, and a malformed digest is dropped rather than forwarded as if real) -> `Ota::ExtractAssetsSha256` -> NVS `assets/download_sha256` -> `Assets::Download`. `download_sha256` is erased alongside `download_url` on success, because a stale hash would fail every future download.
- **Both paths proven on hardware, not argued.** Served a bundle with **one byte flipped at offset 652731** while the gateway advertised the clean hash:
  - `E Assets: Assets SHA-256 mismatch: expected 82040a2f… got a20e7dc0…` -> `Alert: Lỗi: Failed to download assets`. A single flipped byte is exactly what the old 16-bit sum could miss.
  - Then the clean file was restored and the device **retried by itself on the next boot** (`applied_url` was never written), downloaded, verified, and came up on `wn9_hilili_tts`.
- **Download is far faster than the earlier measurement suggested: 20-30 s at 22-39 KB/s**, not the ~6 minutes seen with the 2.5 MB bundle. Halving the bundle plus better conditions. The portal copy was corrected from "vài phút" to "thường dưới một phút" — the earlier number would have been a promise we beat by an order of magnitude in the wrong direction.

## 2026-09-09 — Explained "device keeps re-updating" after 1.7.3: a bootloader rollback loop, not a repeat OTA bug
- User reported the bench device kept auto-updating even after already taking the 1.7.3 OTA. Confirmed live: a passive capture caught it mid-download of the full firmware (3,574,432 B, i.e. xiaozhi.bin again) minutes after it had already been confirmed running 1.7.3 in an earlier capture this same session.
- **Root-caused by reading the flash directly instead of trusting logs alone** (`esptool read_flash` on the partition table, `otadata` at 0xd000, and the first 64KB of both `ota_0` @0x20000 and `ota_1` @0x5a0000, decoding each `esp_app_desc_t` by hand — see scratchpad `otadump/`). Findings: `ota_0` holds a **local dev build from 2026-09-08 17:53:17** labeled `1.7.2` (leftover from the "sfx_codec->PSRAM, version back to 1.7.2" session, not anything from the OTA channel); `ota_1` holds today's real `1.7.3` OTA build (compiled 14:42:26). `otadata` sector 0 = seq 1 (`ota_0`), sector 1 = seq 2 (`ota_1`), both read `VALID` at the time of the final check.
- **Mechanism**: `CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE=y`. A freshly-OTA'd slot is `PENDING_VERIFY` until `Ota::MarkCurrentVersionValid()` runs — and that only happens from the branch in `application.cc:978-979` reached **after** a full `CheckVersion()` round-trip (console pass + GitHub pass) comes back with nothing new (`if (ota_->HasNewVersion()) { ... return; } ota_->MarkCurrentVersionValid();`). If anything interrupts the device before that point in a given boot — crash, reset, watchdog — the slot stays unconfirmed, and the bootloader auto-rolls-back to the other slot on the next boot. On this bench unit that other slot is the stale local 1.7.2, which explains the observed loop exactly: boot old local 1.7.2 -> see 1.7.3 on GitHub -> download/flash/reboot into 1.7.3 (pending) -> interrupted before confirming -> next boot rolls back to local 1.7.2 -> repeat.
- **Honest caveat, not swept under the rug**: this session's own repeated `esptool run` hard-resets during investigation are a real suspect for landing inside that unconfirmed window and triggering at least one of the observed rollbacks on this specific bench unit. Could not fully rule this out as the trigger here.
- **Current state, verified**: both otadata slots read `VALID`, `ota_1` (1.7.3) at the higher sequence number, and the latest clean boot capture confirms `App version: 1.7.3` with no re-download triggered. Settled.
- **Structural risk flagged but NOT fixed this session**: gating "mark valid" behind a full successful network round-trip is fragile given this project's long documented history of intermittent TLS/internal-RAM allocation failures (see 2026-09-02/09-08 entries above) — a real fielded device that stumbles on that specific check right after taking an OTA could roll back to whatever old image is sitting in its other slot, which for a shipped unit could be a much older factory image rather than something close to current. Worth hardening (e.g. mark valid as soon as core services are confirmed up, independent of the OTA check succeeding) but this needs a deliberate decision, not a reflex fix — not done.

## 2026-09-10 — Fixed the touch-during-download crash before shipping 1.7.4
- **Root cause, precisely.** Menu/care icons are resolved once at boot into a raw pointer straight into the assets partition's mmap (`ResolvePersistentAssetImage` in menu_system.cc caches it, never re-fetches per draw). `Assets::Download()` calls `UnApplyPartition()` (assets.cc:445) before writing a single byte, which calls `esp_partition_munmap()` -- every one of those cached pointers is dangling from that instant. `LvglStrategy::UnApplyPartition()` cleared `mmap_root_`/`assets_` but **never reset `partition_valid_` to false**, so `ResolveAssetImage`'s existing `partition_valid()` guard was lying the whole time a download (or a failed one) was in flight. LVGL redrawing a menu icon in that window dereferences the dangling pointer: `Guru Meditation Error: Cache error / MMU entry fault`. And because a failed download (sha256 mismatch, see the entry above) never reaches `InitializePartition()`, this wasn't just a 20-35s window -- an unrecovered failure left it broken for the rest of that boot.
- **Fix, two small pieces:**
  1. `Assets::LvglStrategy::UnApplyPartition()` (assets.cc) now sets `assets->partition_valid_ = false`, matching what the name already claimed to mean.
  2. `MenuSystem::Open()` (menu_system.cc) -- the single entry point from the idle eyes screen into any icon-bearing panel -- checks `Assets::GetInstance().partition_valid()` first and no-ops (tap simply isn't consumed) if it's false, instead of showing a screen that would crash.
  Did **not** touch `Assets::EmoteStrategy` (different board family, different icon-consumption pattern, no hardware to verify against) -- scoped the fix to the board that actually reproduced this.
- **Verified twice on the bench device, on the actual build about to ship:** built clean (no warnings in the three touched files), flashed, NVS wiped to force a genuine re-download (not just re-applying an already-installed bundle), reconnected WiFi, and while `Assets: Progress: NN%` was actively printing, tapped the screen. **No crash, and the screen did not react to the tap** -- exactly the intended no-op, confirmed by the user directly on hardware, not just from logs.
- Also confirms `main/assets.bin` (the icon fix from earlier today) survived: wake word came back up as `wn9_hijoy_tts`, no fallback-to-text warning.

## 2026-09-16 — Downloadable games: evaluated OTA-vs-download before committing (plan doc §0b)
- User pushed back on the prior entry's plan: prove that server-hosted download beats just shipping games in firmware OTA. Fair — the plan had asserted it. Added `docs/downloadable-games-plan.md` §0b with the actual comparison; no code changed.
- **There are four options, not two, and two of them cost no new code.** (A) all in firmware, (B) code in firmware + art in the assets bundle — which is literally the existing menu-icon path — (C) download packs, (D) engines in firmware + content in packs.
- **Decisive number: firmware double-charges.** `SPIRAM_FETCH_INSTRUCTIONS`/`RODATA` mirror the image into PSRAM 1:1 (confirmed on hardware: −206,336 B flash returned +206,136 B PSRAM), so art compiled in costs flash *and* PSRAM, while assets-partition data is mmapped and costs zero PSRAM. Free PSRAM is ~4,169,728 B and the MultiNet→WakeNet switch is what bought it. Option A is the worst home for art and the only one capped by RAM.
- **Art is the whole question, and today there is none** — all 3 games draw with LVGL primitives, zero image assets. The 13 menu/care PNGs average 83,322 B, so **one screen-sized image is ~3.9× the total code of all three games** (21,140 B).
- **Verdict: option D, but not yet.** Fixed cost is ~35-55 KB of firmware in the riskiest subsystem in the tree plus gateway/portal/tooling, against 3 games and a firmware that currently ships weekly anyway. Recommended order: reserve the space now (the only irreversible part), ship the next 1-2 games via firmware+assets-bundle art, **write them as if already data-driven** (tunables in structs, no magic constants in draw code) so the eventual port is serialisation not rewrite, then build the download half on a named trigger (>=8 games / game-only change forcing a firmware release >2x a quarter / art >1.5 MB / per-child catalogs / fleet >~500 devices).
- Counter-argument recorded rather than buried: the weekly firmware cadence makes riding along free *today*, but that cadence is an unstable-period symptom — after production each release costs more to justify, so the risk-coupling argument gets stronger, not weaker. Separately, the best argument for building sooner is that the flash-write path should be shaken out while bugs cost 11 devices instead of 5,000.
- Corrected an error in yesterday's plan: "LVGL binary images are smaller than PNG" is wrong. 240x240 RGB565 is 115,200 B vs 67-108 KB for PNG — it is a flash-for-RAM trade (zero decode, zero RAM), right for 30 Hz sprites, wrong for a shown-once title screen. Pack builder should allow both.

## 2026-09-16 — MẮT XANH: eyes not changing colour / old eyes showing through. Two root causes, fixed. Built, NOT flashed

## 2026-09-17 — Where the firmware's internet time went (audit)
- **The original Bubu firmware did use NTP.** It was an Arduino/PlatformIO build, kept at `references/bubu_ota`: `src/display_system.cpp:1204` calls `configTzTime("ICT-7", "pool.ntp.org", "time.nist.gov")` from `Clock_tryNtpSync`, retrying every 10 s while WiFi is up.
- **SNTP was lost when Bubu was ported to ESP-IDF / xiaozhi-esp32, not when the gateway was built.** The current tree has no SNTP call in `main/` or `managed_components`, and `build/xiaozhi.map` has 0 `sntp` symbols. The oldest IDF release we have (`artifacts/releases/v2.2.4_esp32s3-1.28-round-i80.zip`, dated 2026-03-14) has no SNTP strings either. From that release on, the only clock source is the OTA reply's `server_time` (`ota.cc:278`).
- That v2.2.4 build pointed at `https://api.tenclass.net/xiaozhi/ota/`, xiaozhi's public server, whose clock is kept correct. So the clock stayed right and nobody noticed SNTP was gone. It only broke once `CONFIG_OTA_URL` moved to `api.bubumotion.vn`, whose VPS cannot reach NTP.
- Trap for anyone re-adding SNTP: `ota.cc` adds `timezone_offset` into the epoch itself (the device keeps "local time" as UTC, with no TZ set). SNTP gives true UTC. Mixing the two leaves the device 7 h out whenever one source overwrites the other. Pick one model: true UTC + `TZ=ICT-7`, and stop adding the offset in `ota.cc`.
